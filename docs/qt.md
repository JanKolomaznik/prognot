# Qt 6 integration

## Build and packaging

Enable `PROGNOT_BUILD_QT=ON` with Qt 6.5+ Widgets installed. Link
`prognot::qt`; the target propagates the core and Qt Widgets dependencies.
`cmake --install` installs both targets and all Qt headers when enabled.
An installed Qt-enabled package requires Qt even when loading only its core
export; install with `PROGNOT_BUILD_QT=OFF` for a package with no Qt dependency.
Set `PROGNOT_BUILD_EXAMPLES=ON` to build the simple and stacked GUI examples.
The API reference generated by `doxygen Doxyfile` includes all public Qt headers.

## Safe worker integration

Create, configure UI objects, and destroy them on the GUI thread. All adapter and
widget APIs are GUI-thread only. Create the core handle there and move it to a
worker; the worker never calls a widget or retains a widget pointer:

```cpp
#include <prognot/Qt/ProgressBar.hpp>
#include <thread>

prognot::qt::ProgressBar bar;
std::jthread worker([](std::stop_token stop, prognot::ProgressNotifier task) {
    try {
        task.setStepCount(100);
        for (int i = 0; i < 100; ++i) {
            if (stop.stop_requested()) task.cancel();
            // Perform a unit of work.
            task.increment();
        }
        task.finish();
    } catch (const prognot::CancelException&) {
        // Cooperative cancellation; no completion is synthesized.
    }
}, bar.makeNotifier());
// Run the Qt event loop to display updates. The worker must be joined on shutdown.
```

`QtProgressNotifier::makeNotifier()` creates an owned, non-QObject bridge into the
core. A mutex protects enqueueing against GUI object destruction. Worker events
are always queued, including events reported on the GUI thread. Signals are
emitted on the adapter's thread when its event loop processes them. Queued work
uses the adapter as context and is discarded after its destruction. No widget
pointer is retained by a worker. Destroying the adapter requests cancellation
and detaches delivery without joining workers. The owner must still manage and
join those workers; cancellation cannot interrupt a blocking computation.

Each adapter represents **one operation**. Repeated `makeNotifier()` calls throw
`std::logic_error`; create a new bar/adapter for another run, or clear and add
new tasks to a stacked widget. `progressNotifier()` returns a borrowed adapter
for signal connections and its `cancel()` slot, not an implementation to pass
as a raw pointer to the core's constructor. This is an intentional API change
from the original prototype.

## Signals and cancellation

`started()` precedes updates. Each update emits `progressChanged(Progress)` with
the exact fraction and `incremented(int)` with its percentage rounded down.
Values below one therefore never display 100% prematurely. On lifecycle end,
`stopped(Completion)` is followed by `finished()` if the adapter still exists. Only `Completion::succeeded`
means success. These types are registered with Qt for queued signal connections.
Events preserve the core's per-operation order. `isRunning()` becomes false
when the terminal event is delivered; pending events require a running loop.

`cancel()` requests cancellation directly through the core's shared stop source,
without waiting for a future progress callback. Children observe the same request.
The slot is harmless before `makeNotifier()`; it does not pre-cancel future work.
Avoid blocking slots and never synchronously wait for workers from progress or
stop callbacks. Core reporting exceptions must be handled inside the worker.

`ProgressDialog` wires its Cancel button, Escape, and window close to cancellation
and immediate rejection. Success accepts the dialog; canceled, failed, and
abandoned results reject it. A queued success cannot override an earlier user
rejection. `setText()` changes the description. The dialog is single-operation.

## Nested work versus independent operations

For one algorithm with nested tasks, obtain a root from a bar or dialog and use
core `subTaskNotifier(weight)` handles. Their contributions are already combined
by the core and the widget displays the root's exact fraction.

For several independent operations, use `StackedProgressBar`:

```cpp
prognot::qt::StackedProgressBar group;
auto loading = group.makeNotifier(1);
auto processing = group.makeNotifier(3);
// Move these handles into separate workers, each configuring its own step count.
```

The aggregate is `sum(weight[i] * progress[i]) / sum(weight[i])`. Weights are
positive signed 64-bit integers; invalid weights throw `std::invalid_argument`.
An empty group displays zero. Arithmetic uses exact fractions and an arbitrary
precision weight sum. Only final display conversion rounds down to a percentage.
The popup exposes individual bars when the pointer enters the aggregate;
`showSubtaskWindow()` controls it explicitly.

Register all operations before reporting for a fixed denominator. Adding a task
later changes the denominator and can lower the aggregate. Completed, failed,
and canceled operations keep their weight and last delivered fraction until
`clear()`; cancellation never counts as 100%. `cancel()` requests cancellation
of all registered operations. `clear()` cancels existing operations, destroys
all bars, discards their pending updates, and resets the group to zero. Surviving
core handles remain safe but canceled. New tasks form a fresh group.

`createProgressNotifier(weight)` adds a bar but returns its borrowed adapter
without starting it, allowing signal connections before `makeNotifier()`.
Direct deletion of borrowed adapters or child bars is unsupported; use `clear()`
or destroy the owner. `ProgressBarStack` is the lower-level popup container and
can also be used independently.

## Configurable popup

`PopupProgressBar` inherits the weighted task API and ownership rules of
`StackedProgressBar`. It defaults to left-click activation and downward placement:

```cpp
#include <prognot/Qt/PopupProgressBar.hpp>
using prognot::qt::PopupProgressBar;
PopupProgressBar group;
group.setPopupDirection(PopupProgressBar::PopupDirection::Right);
group.setPopupTrigger(PopupProgressBar::PopupTrigger::Hover);
auto loading = group.makeNotifier(1);
auto processing = group.makeNotifier(3);
```

Directions are `Up`, `Down`, `Left`, and `Right`. Placement is clamped to the
screen's available geometry. `Click` toggles details with the left mouse button;
`Hover` opens them on pointer entry and leaves them available for inspection.
Escape or clicking outside dismisses the Qt popup. Changing the trigger hides
an open popup. `showSubtaskWindow(bool)` works with either trigger, and
`isSubtaskWindowVisible()` reports its current visibility. Hiding the owner also
hides details. These are views of registered independent operations; nested core
handles still contribute through their root and do not create extra UI rows.
